SOP
Working agreement

LKC + DEV

How the roles work together on internal product builds: who owns what, what has to be true at each handoff, how the day runs across timezones, and how the spec side and the build side split AI-assisted work without both building the same thing.

Status

Draft for confirmation. The APPROVER owns the roles and decision rights in section 1. The LKC and the DEV own the cadence in section 3 and should set the times to what they will actually keep. Everything else follows the App Development Playbook and does not change locally.

This document names roles, not people

A role is a set of responsibilities, not a person. One person can hold two roles, and a role can later be held by several people. Written this way, the agreement survives someone changing jobs, a second developer joining, or the knowledge side growing into a group of subject-matter experts.

1 · Roles and decision rights

Three roles. Today they are filled by fewer than three people, which works only if the boundary between roles stays explicit even when one person is standing on both sides of it.

LKC

Lead Knowledge Consultant

Spec and verification
  • Writes PRDs and item descriptions
  • Writes acceptance criteria
  • Keeps the board honest: epics, releases, tags, duplicates
  • Verifies items in staging against every criterion
  • Writes the release note line on each item as it passes Done
  • Escalates open decisions to the APPROVER
DEV

Software Developer

Build
  • Estimates items entering Ready
  • Builds, using AI tools as they choose
  • Self-reviews the diff before In Review
  • Deploys to staging and names what to test
  • Flags scope and technical risk early
  • Writes the consolidated release note for each release
  • Owns the repo, branches and environments
APP

Approver

CEO or a Director
  • Sets priority and backlog order
  • Rules on decision gates
  • Approves releases
  • Approves anything touching money, client data or compliance
When the LKC role grows

The LKC role is expected to widen as more subject-matter experts get involved. When it does, one rule keeps it working: one named LKC owns each item from spec through verification. The person who wrote the acceptance criteria is the person who checks them. Splitting spec and verification across two people breaks the chain, because the criteria stop being written by someone who knows they will have to test them.

Multiple LKCs can each own different items in the same release. The board shows who owns what, so nothing depends on remembering.

The one conflict to watch

The LKC writes the criteria and also verifies against them. That is efficient and it is also a blind spot: a criterion written vaguely will be verified vaguely by the same person. The guard is the DEV challenges the criteria before the item enters Ready, not after the build. If a criterion does not say exactly what has to be made true, the DEV says so then.

2 · The four handoffs

Work crosses between the roles four times. Each crossing has a contract: things that must be true before it moves. A handoff missing its contract bounces back, and that is not a criticism, it is the process working.

LKC→DEV Handoff 1 · Spec to estimate

The LKC hands over: a drafted item or PRD with goal, why it matters, current and desired behavior, acceptance criteria, out of scope, and do not break.

The DEV replies with:

  • An estimate, or a request to split if it is 13 or above
  • Any criterion that cannot be verified from the wording
  • Any technical dependency the spec missed
  • Any "do not break" item the spec should have listed and did not

Target: replied to within one working day. An item can sit in Backlog indefinitely; an item waiting on an estimate blocks a release plan.

LKC→DEV Handoff 2 · Ready to build

Contract: the item passes all twelve Definition of Ready checks. Epic linked, release set, owner set, priority set, estimated, no open decision gates, dependencies linked, not a duplicate.

What this buys: the DEV never has to stop mid-build to hunt for an answer, and the LKC never has to reconstruct an intention a week later. If an item reaches In Progress and a question appears anyway, that is a signal the Ready gate was rushed, and it is worth saying so out loud.

DEV→LKC Handoff 3 · Build to verify

The DEV posts a HANDOFF: comment naming:

  • Where it is deployed, and the URL or environment
  • Which acceptance criteria are ready to check
  • Any test account, seeded data or setup needed to reach the flow
  • Anything already known to fail, and why
  • The AI build record, if a tool built it

Contract: the self-review checklist has been run and the branch is merged or ready to merge. "It should work" is not a handoff. If the DEV has not opened the flow since the last change, it is not ready to hand over.

LKC→DEV Handoff 4 · Verify result

The LKC posts a TESTED: comment, criterion by criterion. Not "looks good" and not "still broken." Which numbers passed, which failed, and for each failure what was done and what was seen.

If everything passes: the LKC completes the Definition of Done, sets the completion date, attaches the release, writes the release note line and moves it to Done. If anything fails: the item goes back to In Progress with the failing criteria named. It does not go back with a new criterion attached, because that is a new item.

The rule that makes all four work

Every handoff happens in a comment on the item, not in chat. Chat is for nudging someone to go look at the item. The item is where the record lives, because in three months the chat is unfindable and the item is not.

3 · The daily rhythm

The LKC and the DEV share working hours, so they have a full overlapping day. The APPROVER works a different timezone, so anything needing that role is overnight async. The whole cadence follows from that one fact.

START OF DAY
Read the board Anything the APPROVER answered overnight is waiting. The LKC clears rulings into the items they unblock. The DEV picks up whatever became Ready.
MIDDAY
Sync window LKC and DEV overlap fully. Estimates, criteria challenges, anything needing a real conversation happens here rather than in a comment thread.
AFTERNOON
Build and verify Heads-down. Handoffs 3 and 4 land here so nothing waits a full day for a check.
END OF DAY
Queue for the APPROVER Everything needing a ruling gets posted before logging off, so it lands at the start of their day and is answered by the next morning.

The rhythm in rules

  • Queue anything for the APPROVER before you log off. A question raised at the start of your day and one raised at the end of it get answered at the same time. Raising it early changes nothing; raising it late costs a day.
  • Batch the asks. One message with four decisions beats four messages with one each.
  • Never sit idle waiting on a ruling. Tag the item needs-decision, leave it in Backlog, and pull the next Ready item.
  • The weekly checkpoint is thirty minutes, walking the board right to left. Section 05 of the playbook has the agenda. If it runs long, the board was inaccurate, and fixing that is the real outcome of the meeting.

Blocked is a state, not a mood

The moment you cannot continue, post a BLOCKED: comment naming what you need and which role can give it. Do not wait to see whether it resolves itself, and do not carry it silently to the next sync. An unposted blocker is invisible, and invisible blockers are what turn a two-day item into a two-week one.

4 · Splitting AI-assisted work

Both the LKC and the DEV use AI tools. That creates two failure modes worth naming: collision, where both generate a version of the same thing, and unreviewed acceptance, where generated code lands because it looked finished. The rules below exist for those two.

The LKC prompts for

  • PRDs and item descriptions
  • Acceptance criteria drafts
  • Release note lines on individual items
  • The two Sprints skills, for filing and decomposition
  • Research and comparison work

The LKC owns the spec the build tool receives.

The DEV prompts for

  • Implementation, from the approved spec
  • Refactors and migrations
  • Test scaffolding
  • Debugging and error investigation
  • The consolidated release note

The DEV owns the code the tool produces, including the parts nobody typed.

The seven rules

  1. One spec, one owner. The item description and the PRD belong to the LKC. If the DEV needs the spec changed to build it, the DEV says so and the LKC changes it. The DEV does not fork a different version into a prompt, because then two specs exist and only one is on the board.
  2. Nobody starts a build that is not in In Progress with their name on it. That is the entire collision guard. Check the board before you prompt.
  3. The prompt gets attached. Every AI-built item carries the NOTE: AI build record comment with the tool, the date, the spec handed over, and any deviation kept. The question in three months is "what did we ask for," and this is the only place with the answer.
  4. Generated code is reviewed by a person before In Review. The DEV reads the whole diff against the acceptance criteria, not against a memory of the prompt. Deletions get the most attention.
  5. The AI never closes the loop. A tool reporting success is a claim. The LKC verifies in staging, criterion by criterion, and posts TESTED:. This does not scale down for small items.
  6. Scope creep from a tool is scope creep. If a one-line fix came back touching nine files, that needs an explanation on the item before it merges, not after.
  7. Nothing confidential goes into a prompt. No client data, no employee data, no credentials, no production database contents. If a key was ever pasted into a tool, it gets rotated.
Why the split works this way

When AI writes the code, the spec is the engineering artifact and the code is the output. That puts the highest-leverage work at the front, with the LKC, and the highest-risk review at the back, with the DEV. Reversing it, where the builder writes the spec they then build from, removes the only independent check in a small team.

5 · When things do not go to plan

The DEV disagrees with a criterionSay so before Ready. If it still cannot be resolved, the APPROVER rules. Do not build a different interpretation quietly

Scope grows mid-buildThe DEV posts BLOCKED: or QUESTION:. The LKC edits the description first, then posts DECISION:. If it changes the release, the APPROVER decides
An item bounces back twiceStop and talk in the sync window. Two bounces means the criteria are ambiguous, not that the build is careless
Someone is out sick or on leavePost it on the item before you go, not in chat. Anything In Progress goes back to Ready with a comment on where it stands
Production breaks after a releaseRoll back first, diagnose after. File the Bug, tell the APPROVER the same day, and note the cause on the release

Two people worked on the same thingKeep the version matching the spec, close the other, and note on the item how the collision happened so rule 2 gets tightened

7 · Open items before this is final

Needs confirming
  • The sync window time. Section 3 says midday. Pick a real time both roles will keep.
  • Staging. Handoffs 3 and 4 assume a staging environment exists with fake data and that the LKC can reach it. Confirm what exists today and correct section 2 if it does not.
  • Release approval. The table says the APPROVER, or the LKC on a pre-approved release. Confirm whether the LKC ever releases alone.
  • The weekly checkpoint slot. Thirty minutes, day and time to be set.
  • The APPROVER's unreachable window. Section 5 lets a reversible low-risk call be made without that role. Confirm this is wanted, and what counts as low risk.
  • Who currently holds each role, recorded somewhere outside this document so the agreement stays role-based and the roster stays current.

A work item is a request for work, written before the work happens, in enough detail that a second person can build it and a third person can confirm it works.
