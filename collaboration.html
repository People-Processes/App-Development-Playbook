SOP
Working agreement

Dolie + Lucky

How the two of you work together on internal product builds: who owns what, what has to be true at each handoff, how the day runs across Philippines and US hours, and how you split AI-assisted work without both building the same thing.

Status

Draft for confirmation. Rhamy owns the roles and decision rights in section 1. Dolie and Lucky own the cadence in section 3 and should adjust the times to what they will actually keep. Everything else follows the App Development Playbook and does not change locally.

1 · Roles and decision rights

Two people, three roles. Dolie carries two of them, which works only if the boundary between them stays explicit.

D

Dolie

Spec writer and verifier
  • Writes PRDs and item descriptions
  • Writes acceptance criteria
  • Keeps the board honest: epics, releases, tags, duplicates
  • Verifies items in staging against every criterion
  • Writes the release note line on each item as it passes Done
  • Escalates open decisions to Rhamy
L

Lucky

Builder
  • Estimates items entering Ready
  • Builds, using AI tools as she chooses
  • Self-reviews the diff before In Review
  • Deploys to staging and names what to test
  • Flags scope and technical risk early
  • Writes the consolidated release note for each release
  • Owns the repo, branches and environments
R

Rhamy

Product owner
  • Sets priority and backlog order
  • Rules on decision gates
  • Approves releases
  • Approves anything touching money, client data or compliance

The one conflict to watch

Dolie writes the criteria and also verifies against them. That is efficient and it is also a blind spot: a criterion written vaguely will be verified vaguely by the same person. The guard is Lucky challenges the criteria before the item enters Ready, not after the build. If a criterion does not tell her exactly what she has to make true, she says so then.

2 · The four handoffs

Work crosses between the two of you four times. Each crossing has a contract: things that must be true before it moves. A handoff missing its contract bounces back, and that is not a criticism, it is the process working.

Dolie→Lucky Handoff 1 · Spec to estimate

Dolie hands over: a drafted item or PRD with goal, why it matters, current and desired behavior, acceptance criteria, out of scope, and do not break.

Lucky replies with:

  • An estimate, or a request to split if it is 13 or above
  • Any criterion she cannot verify from the wording
  • Any technical dependency the spec missed
  • Any "do not break" item the spec should have listed and did not

Target: replied to within one working day. An item can sit in Backlog indefinitely; an item waiting on an estimate blocks a release plan.

Dolie→Lucky Handoff 2 · Ready to build

Contract: the item passes all twelve Definition of Ready checks. Epic linked, release set, owner set, priority set, estimated, no open decision gates, dependencies linked, not a duplicate.

What this buys: Lucky never has to stop mid-build to hunt for an answer, and Dolie never has to reconstruct what she meant a week later. If an item reaches In Progress and a question appears anyway, that is a signal the Ready gate was rushed, and it is worth saying so out loud.

Lucky→Dolie Handoff 3 · Build to verify

Lucky posts a HANDOFF: comment naming:

  • Where it is deployed, and the URL or environment
  • Which acceptance criteria are ready to check
  • Any test account, seeded data or setup needed to reach the flow
  • Anything she already knows will fail, and why
  • The AI build record, if a tool built it

Contract: the self-review checklist has been run and the branch is merged or ready to merge. "It should work" is not a handoff. If Lucky has not opened the flow herself since the last change, it is not ready to hand over.

Dolie→Lucky Handoff 4 · Verify result

Dolie posts a TESTED: comment, criterion by criterion. Not "looks good" and not "still broken." Which numbers passed, which failed, and for each failure what she did and what she saw.

If everything passes: she completes the Definition of Done, sets the completion date, attaches the release, writes the release note line and moves it to Done. If anything fails: the item goes back to In Progress with the failing criteria named. It does not go back with a new criterion attached, because that is a new item.

The rule that makes all four work

Every handoff happens in a comment on the item, not in chat. Chat is for nudging someone to go look at the item. The item is where the record lives, because in three months the chat is unfindable and the item is not.

3 · The daily rhythm

Dolie and Lucky both work Philippines hours, so they share a full working day. Rhamy is in the United States, so anything needing him is overnight async. The whole cadence follows from that one fact.

PH MORNING
Read the board Anything Rhamy answered overnight is waiting. Dolie clears rulings into the items they unblock. Lucky picks up whatever became Ready.
PH MIDDAY
Sync window The two of you overlap fully. Estimates, criteria challenges, anything needing a real conversation happens here rather than in a comment thread.
PH AFTERNOON
Build and verify Heads-down. Handoffs 3 and 4 land here so nothing waits a full day for a check.
PH END OF DAY
Queue for Rhamy Everything needing a ruling gets posted before you log off, so it lands at the start of his day and is answered by your morning.

The rhythm in rules

  • Queue anything for Rhamy before you log off. A question raised at the start of your day and a question raised at the end of it both get answered at the same time. Raising it early changes nothing; raising it late costs a day.
  • Batch the asks. One message with four decisions beats four messages with one each.
  • Never sit idle waiting on a ruling. Tag the item needs-decision, leave it in Backlog, and pull the next Ready item.
  • The weekly checkpoint is thirty minutes, walking the board right to left. Section 05 of the playbook has the agenda. If it runs long, the board was inaccurate, and fixing that is the real outcome of the meeting.

Blocked is a state, not a mood

The moment you cannot continue, post a BLOCKED: comment naming what you need and who can give it. Do not wait to see whether it resolves itself, and do not carry it silently to the next sync. An unposted blocker is invisible, and invisible blockers are what turn a two-day item into a two-week one.

4 · Splitting AI-assisted work

Both of you use AI tools. That creates two failure modes worth naming: collision, where you both generate a version of the same thing, and unreviewed acceptance, where generated code lands because it looked finished. The rules below exist for those two.

Dolie prompts for

  • PRDs and item descriptions
  • Acceptance criteria drafts
  • Release notes
  • The two Sprints skills, for filing and decomposition
  • Research and comparison work

Not the consolidated release note. Dolie writes the one-line entry on each item at verification. Lucky assembles the release note itself, from what actually shipped.

She owns the spec the build tool receives.

Lucky prompts for

  • Implementation, from the approved spec
  • Refactors and migrations
  • Test scaffolding
  • Debugging and error investigation

He owns the code the tool produces, including the parts she did not type.

The seven rules

  1. One spec, one owner. The item description and the PRD are Dolie's. If Lucky needs the spec changed to build it, Lucky says so and Dolie changes it. Lucky does not fork a different version into a prompt, because then two specs exist and only one is on the board.
  2. Nobody starts a build that is not in In Progress with their name on it. That is the entire collision guard. Check the board before you prompt.
  3. The prompt gets attached. Every AI-built item carries the NOTE: AI build record comment with the tool, the date, the spec handed over, and any deviation kept. The question in three months is "what did we ask for," and this is the only place with the answer.
  4. Generated code is reviewed by a person before In Review. Lucky reads the whole diff against the acceptance criteria, not against her memory of the prompt. Deletions get the most attention.
  5. The AI never closes the loop. A tool reporting success is a claim. Dolie verifies in staging, criterion by criterion, and posts TESTED:. This does not scale down for small items.
  6. Scope creep from a tool is scope creep. If a one-line fix came back touching nine files, that needs an explanation on the item before it merges, not after.
  7. Nothing confidential goes into a prompt. No client data, no employee data, no credentials, no production database contents. If a key was ever pasted into a tool, it gets rotated.
Why the split works this way

When AI writes the code, the spec is the engineering artifact and the code is the output. That puts the highest-leverage work at the front, with Dolie, and the highest-risk review at the back, with Lucky. Reversing it, where the builder writes the spec they then build from, removes the only independent check in a two-person team.

Needs confirming

  • Staging. Handoffs 3 and 4 assume a staging environment exists with fake data and that Dolie can reach it. Confirm what exists today and correct section 2 if it does not.

A work item is a request for work, written before the work happens, in enough detail that a second person can build it and a third person can confirm it works.
