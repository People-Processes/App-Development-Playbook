Claude Skills Guide

Two skills apply the App Development Playbook for you. They draft to the templates, run the gates, and create work in Zoho Sprints after you approve. This page is the full reference: what each does, how to trigger it, what it will ask for, what it refuses, and what to do when something fails.

The one thing to remember

These skills are a drafting and filing assistant, not an authority. They never write to the board without your explicit approval, and creating an item is not the same as building or verifying it.

The two skills

sprints-work-item

Turns a request, a defect report or a piece of engineering work into a correctly written Story, Task or Bug, then creates it in Sprints.

It does:

  • Classifies the type from the decision tree
  • Writes the title to the convention
  • Fills the matching description template
  • Drafts acceptance criteria for you to confirm
  • Runs the twelve Definition of Ready checks
  • Searches the board for duplicates
  • Splits compound requests into separate items
  • Creates the item and attaches epic and release

sprints-prd

Writes the ten-section PRD, decomposes it into an epic, a release and an item list, and creates all of it.

It does:

  • Checks first whether a PRD is even needed
  • Writes all ten sections, including the three people skip
  • Writes the spec in two layers when AI will build it
  • Turns each scope line into an item
  • Sequences the items and names the blockers
  • Creates the epic, the release and every item
  • Refuses to leave a release goal empty
  • Saves the PRD to the repo path

The third skill: release notes

release-notes · owned by Lucky

Writes the internal release note from the items in a Zoho Sprints release, in the playbook format. Produces three things every time: the full note as a markdown file for /docs/releases/, an optional comment posted on the release in Sprints, and a short version for the team channel.

Before it writes anything it reports:

  • Items in the release not yet at Done
  • Items with no TESTED: comment, since nothing ships unverified
  • An empty release goal, and offers to write one
  • Anything with an open decision gate or tagged blocked

Triggers:

write the release notes what shipped in R2 we are releasing today what changed for users post the release note
There are two versions of this one

The account skill reads Zoho Sprints, and works wherever the Sprints connector is available. Claude Code inside the Replit project has no Sprints connector, so a second version lives in the repo at .claude/skills/release-notes/SKILL.md and reads git history instead: merges, branch names, and the item numbers in commit messages. Same output format, two sources.

Setup instructions, including the full file to paste, are in docs/CREATE-RELEASE-NOTES-SKILL-IN-REPLIT.md in this repository.

Worth doing occasionally

Run both versions on the same release and compare. A merge in git with no matching Sprints item means either unfiled work shipped or an item number is missing from a commit message. Both are real findings.

How to trigger them

Say what you want in plain language. The skill picks itself up from the phrasing. There is no command to memorise.

sprints-work-item triggers

file this as a bug create a work item add this to Sprints log this bug write this up as a ticket put this on the board turn this feedback into items

sprints-prd triggers

write a PRD spec this feature plan this build break this into an epic set up a release scope this out turn this plan into Sprints items

Describing the work also works. "A BP says the handbook list is unusable past 50 handbooks" picks up the work-item skill on its own.

What happens during a run

What it will ask you for

It asks for what the gates need and it cannot infer, all in one message rather than one question at a time. Have these ready and a run takes a single exchange.

It will askBecause
Steps to reproduce, for a bugA defect nobody can reproduce does not get fixed. It will not draft around a missing repro
Which epicAn item with no epic disappears from every rollup view
Priority and ownerBoth are Definition of Ready checks
An estimateOnly for items heading to Ready. It refuses to create anything sized 13 or above and offers a split instead
A ruling on any open decisionAn item with an open decision gate cannot enter Ready
Whether a near-duplicate it found is the same workIt searches the board before creating anything
A target date and owner, for a releaseThe Sprints API requires start date, end date and owner on a release

Worked run: one work item

You:    A BP says the handbook list is unusable once a client has
        more than 50 handbooks. She scrolls for a minute to find one.
        File this.

Claude: Type: Story. A user would notice it, and nothing is broken.
        Title: Add search bar to handbook list filtered by handbook name

        ## Goal
        A BP can find a client handbook by typing part of its name.

        ## Why it matters
        BPs with large clients scroll a list of 50+ handbooks to reach
        one. It costs a minute per lookup, several times a day.

        ## Acceptance criteria
        - [ ] Typing three characters filters the list within one second
        - [ ] Clearing the box restores the full list
        - [ ] A search with no match shows "No handbooks found"
        - [ ] The filter matches anywhere in the name, not only the start

        [out of scope, do not break, source references]

        Definition of Ready: 10 of 12 pass.
        Missing: epic, and an estimate.
        No duplicate found (searched "search", "handbook list").

        Which epic, and do you want me to size it? My read is 5 points.

You:    Handbook Builder epic, 5 points, medium priority, Lucky owns it.

Claude: [final field table]  Approve and I will create it.

You:    Go.

Claude: Created ADV-215 in Backlog.
        Epic: Handbook Builder & Policy Editor · 5 points · Medium · Lucky
        Nothing left open. It passes DoR, so move it to Ready when you
        are ready to schedule it.

What they refuse to do

Hard rules, built in
  • Create anything without your explicit approval.
  • Invent acceptance criteria you have not agreed to.
  • Write a description whose content is only an image.
  • Put client or employee personal information into a title, description, comment or attachment, screenshots included.
  • Write a title in past tense.
  • Create an item sized 13 or above without splitting it.
  • File an open question as an item.
  • Leave a release goal empty.
  • Split one outcome across two items, or merge two outcomes into one.

Two things they cannot do

Upload attachments

The Sprints connector has no attachment endpoint. Screenshots, recordings and design files get attached by hand in the Sprints UI. The skill lists which items are waiting on one so nothing gets forgotten.

Verify anything

Filing is not building, and building is not verifying. The human verification gate applies unchanged: a person opens the running app, walks every criterion, and posts a TESTED: comment.

When something goes wrong

SymptomCauseFix
The skill did not triggerThe phrasing did not matchSay "use the sprints-work-item skill" or "use the sprints-prd skill" outright
"Given URL is wrong"Wrong workspace or project IDAsk it to re-run GetProjects and confirm the IDs before retrying
Create failed and the description was longThe description travels as a query parameter and has a practical limit near 4,000 charactersKeep the summary and criteria in the item, move the full spec to /docs/prd/, and reference the path
The description shows literal ## in SprintsMarkdown was sent to a rich-text fieldThe skills convert to HTML before sending. If you see this, ask it to re-send the description as HTML
It keeps asking for steps to reproduceIt will not draft a bug report around a missing reproGive the steps, or reclassify it as a Story if nothing is actually broken
It refuses to create the itemUsually an open decision gate, a 13-point estimate, or PII in the draftIt will name which. Resolve that specific thing
It created a duplicate anywayThe existing item was worded differently enough to miss the searchLink both, close the newer one, comment NOTE: duplicate of ADV-###

Good habits

  • Paste the raw material, not a summary. The client's own words carry detail your summary drops, and the skill is good at pulling structure out of mess.
  • Let it split things. If you paste five requests, it will produce five items. That is correct, not over-eager.
  • Read the acceptance criteria before approving. Everything downstream, including whether the thing can ever be marked Done, rests on them.
  • Answer the batch of questions in one message. A run should be two exchanges, not six.
  • Say no. If the draft is wrong, say what is wrong. Redrafting costs seconds; a wrong item on the board costs a build.
Where the skills live

Both are saved to the account and available in any session. Updating one means saving a new version of the skill, not editing a file. If the playbook changes, the skills need the same change or they will keep enforcing the old standard.
