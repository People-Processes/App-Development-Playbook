00
Start here

One rule holds it all together

A work item is a request for work, written before the work happens, in enough detail that a second person can build it and a third person can confirm it works.

Everything below serves that sentence. If a rule ever feels arbitrary, trace it back to the rule above and it will make sense.

Three roles. One person often wears more than one.

The requester

Describes the problem and what a good outcome looks like. Owns the why. Does not need to write code or know how it will be built.

The builder

Turns the request into working software. Owns the how, the estimate, and the honesty about what is finished.

The verifier

Opens the running app and checks each acceptance criterion. Owns is it actually done. Never the AI. Always a person.

Reading path

New to the team: sections 01 to 09 in order, then keep 16 open while you file your first few items. Filing but not building: 03, 04, 07, 08 and 09. Building: everything, and section 15 twice.

01
Structure

How the work is organized

Four containers. Each answers exactly one question and nothing else. Confusing them is the fastest way to turn a board into a list nobody trusts.

ContainerAnswersLifespanCreated by
ProjectWhich productPermanentSet up once, rarely changes
EpicWhich capabilityMonths, until the capability is completeCreated from an approved PRD
ReleaseWhich shipmentClosed the day it deploysCreated when a shipment is planned
ItemWhich piece of workDaysAnyone, any time
Test yourself

"Handbook Builder" is a capability, so it is an epic. "Everything landing on 13 September" is a shipment, so it is a release. "Add a search bar to the handbook list" is one outcome, so it is an item. If what you want to create does not fit one of those sentences, it is probably two things.

02
Lifecycle

The lifecycle of a change

Every change travels the same six steps. Only the size of each step changes.

Why the gates are worth the friction

Ten minutes making an item Ready removes the mid-build stall where the builder stops to hunt for an answer. Five minutes verifying removes the much more expensive discovery, weeks later and by a user, that a feature never worked.

Why work flows one way

Any backward move other than a failed criterion means the item was started before it was understood. That is exactly what the Ready gate exists to prevent.

03
Intake

How work enters, and what gets done first

Every request enters the same way

Work starts as an item on the board. Not a chat message, not a screenshot in a huddle, not a verbal ask on a call. If it is worth building, it is worth thirty seconds of writing down. A request living only in a conversation is invisible the moment the conversation ends.

Triage: one question

Ask this

Is this bigger than roughly a week of work, or does it change how a user thinks about the product?

  • No. Write a single item using the templates in section 16. That is the whole process.
  • Yes. Write a PRD first, then break it into an epic and items.

One override: anything carrying an unresolved business decision needs a PRD regardless of size. A decision buried in an item description gets missed. A decision in a PRD has a home, a number and an owner.

Priority

Priority is a field on the item, set by the person who owns the backlog. Not decided in conversation, and not decided by whoever asked most recently.

PriorityDefinitionWhat happens
HighA user is blocked, data is wrong, money is wrong, or another item cannot start until this is donePicked up next
MediumReal value, nobody is blockedScheduled into the current release
NoneWanted, not scheduled yetSits in Backlog until promoted
The express lane

A defect blocking a client in production skips the queue. File it as a Bug, tag it client-reported, set priority High, and tell the backlog owner the same day. It goes to the top of In Progress even if something else has to be put down mid-build.

One item, one outcome

An item describes one thing a person could verify as working or not working. If the title needs a semicolon or the word "and" to be accurate, it is two items. Split it.

Before filing, search the board for a duplicate. Searching takes ten seconds. Two people building the same thing takes days.

04
Specification

The PRD

A PRD is a Product Requirements Document: the written plan for a feature, agreed before anyone builds it. It answers what problem we are solving, for whom, what the finished thing does, and how we will know it works.

When a PRD is required

  • The work is bigger than roughly one week.
  • It changes a user-facing workflow.
  • It touches money, client data, or compliance evidence.
  • It carries an open business decision.
  • It is going to be handed to an AI tool to build. See section 15.

The ten sections, and what each is for

SectionWhat goes in itWhy it exists
1. ProblemWhat is wrong or missing today, from the user's sideA feature without a problem is a preference
2. Who this is forThe specific user role"Users" is not a role. BP, client admin, employee, internal admin are roles
3. Current behaviorWhat happens today, step by step, including workaroundsReveals whether the problem is real and how people cope
4. Desired behaviorWhat happens instead, naming screens and buttonsThe builder's blueprint. Vague here means wrong later
5. ScopeIn scope and out of scope, both numberedOut of scope prevents more mid-build argument than any other section
6. Acceptance criteriaNumbered, testable statementsThe definition of finished, agreed in advance
7. Do not breakExisting behavior that must keep workingNames the blast radius before anyone touches the code
8. Decision gatesOpen questions, numbered DG-1, DG-2, with an ownerMakes unresolved decisions visible instead of buried
9. Risks and dependenciesWhat could go wrong, what must happen firstSequencing and rollback planning
10. Source referencesFiles, tickets, prior docs, recordingsLets the next person reconstruct the reasoning
The three people skip

Out of scope, Do not break and Decision gates. Those three are where the rework comes from. Write them even when they feel obvious, because obvious to you today is not obvious to anyone in three months, and never obvious to an AI tool.

Where a PRD lives

The repository is canonical. PRDs live under /docs/prd/ as Markdown, named YYYY-MM-DD-feature-name.md. The Sprints epic carries a one-paragraph summary and a link. Keeping the spec next to the code makes it versioned, reviewable, and findable by anyone with repo access rather than by one person with the right folder open.

05
The board

Six columns, and what moving a card means

The board is a Kanban board: work flows left to right through fixed stages, with a cap on how much sits in progress at once. The column an item is in is a public statement about its state, so moving a card is a claim you make to everyone else.

ColumnWhat it meansWhat you claim by moving here
BacklogFiled, not ready to buildNothing. Anyone files here
ReadyPasses the Definition of ReadySomeone could pick this up right now with no questions
In ProgressBeing built right now. Maximum 3I started, and I own it
In ReviewCode written, review pendingThe branch is pushed and the self-review checklist has been run
For TestingDeployed where a human can click itSomeone else can verify now, and I said where and what to check
DoneVerified and releasedEvery acceptance criterion passed and a person confirmed it

Why the limit of three

A WIP limit caps how many items sit in In Progress at once. Three is the cap for a single builder. Half-finished work has all the cost of work and none of the value, and switching between five things makes every one of them slower. When you hit the limit, finish something before starting anything.

The weekly checkpoint

Thirty minutes, once a week. Walk the board right to left, which surfaces the work closest to shipping first.

  1. What is stuck, and what would unstick it?
  2. Anything in In Progress over a week gets split or unblocked.
  3. Review everything tagged needs-decision. Rule on it, or name who will and by when.
  4. Pull the next items into Ready and estimate them.
  5. Confirm what is still landing in the current release.

If the board is accurate, the meeting is short. If the meeting is long, the board was not accurate.

06
Item types

Story, Task, or Bug

Three types. The type drives how the item is written, how it is prioritized, and what it tells us about quality over time. Click a card to flip it.

StoryA change a user would notice and could describe in their own words. Delivers value on its own.CLICK TO FLIP
Example

"Add a search bar to the handbook list so a BP can find a handbook by name."

Written from the user's point of view, never the code's. Gets three to seven acceptance criteria.

TaskAn engineering step with no standalone user value. Groundwork, config, migration, refactor, research.CLICK TO FLIP
Example

"Add a database index on policies.state_code."

Always names the story it enables. A task enabling nothing is a task nobody needs.

BugBehavior in a shipped build is wrong. Something worked, or was supposed to, and does not.CLICK TO FLIP
Example

"Clicking Send for Review spins forever and never sends."

If it never worked and was never promised, it is a Story. Steps to reproduce is the whole report.

Try it

Which type is it?

Is the app doing something wrong right now, in a build a user can reach?
Would a user notice this change and be able to describe it in their own words?

Two things that are not items

  • An open question. "Should we allow .docx uploads?" is a decision, not work. It belongs in a PRD as a decision gate, or on the item it blocks, tagged needs-decision.
  • An aspiration. "Make the dashboard better" has no acceptance criteria, so it has no finish line. Turn it into the specific changes you want, or leave it as a note until you can.

08
Writing

Writing the item

The title

Format: verb, object, qualifier. Present tense, imperative, because the title describes work to be done rather than work already finished.

Write it like this

  • Add search bar to handbook list filtered by handbook name
  • Fix Reset to Original button so changes apply without a page refresh
  • Remove Hours Tracking tab from the Advisor dashboard

Not like this

  • TOC reorder · no verb, no context
  • update dashboard booking to use it · use what
  • improved the export layout · past tense, describes finished work
  • Add tab; build page; wire API · three items in one
RuleReason
Present tense, imperative verbThe board holds requests, not a changelog. Past tense means the item was filed after the fact
One outcome. No semicolons, no "and"An item with two outcomes cannot be marked done, because half of it can pass
Under 90 charactersLonger titles get truncated in every board view, hiding the important half
No emoji, no status markers, no arrowsStatus lives in the column. A title saying "done" will still say it tomorrow
Specific enough to search"Fix sizing" finds nothing in six months. "Fix BP dashboard table overflow under 1280px" finds itself
No leading dash, no trailing space, no double spaceSorting and search both break on invisible characters
Title fixer

Pick the title that follows the rules

Someone filed: "fixed the spinner thing on review"

Score: 0 of 0

The description

Three templates, one per type. Full copy-paste versions in section 16. The story template is the one you will use most.

## Goal
One sentence. What a user will be able to do after this ships.

## Why it matters
Two or three sentences in plain English. Who is affected, what it costs
them today. A non-developer should understand this section completely.

## Current behavior
What happens today. Numbered steps if a flow is involved.

## Desired behavior
What happens instead. Numbered steps. Name the screens and the buttons.

## Acceptance criteria
- [ ] Testable statement 1
- [ ] Testable statement 2

## Out of scope
What this item does not cover.

## Do not break
Existing behavior that must keep working.

## Dependencies
Items or decisions blocking this. Link them, do not type the number.

## Source references
PRD link, files, screenshots, recordings, ticket numbers.
The screenshot rule

An image supplements words. It never replaces them. A description containing only a pasted screenshot is not searchable, does not survive an export, and does not tell the reader what to look at. Write the steps in words, attach the image as a file, and add one line naming what is in it: "See the Compliance Review panel, top right, results list is empty after switching policies."

Making open decisions visible

An unresolved decision inside a description is invisible from the board. Surface it three ways so it cannot be missed.

  1. Tag the item needs-decision.
  2. Put the question in an ## Open decisions section at the top of the description, numbered DG-1, DG-2.
  3. Name who must rule and by when. Record the ruling inline with its date, then remove the tag.
## Open decisions
DG-1: Retention window for the email log. Default indefinite.
      Needs: APPROVER. Blocks: schema design. Status: OPEN
DG-2: Absorb the existing log table or run parallel.
      Needs: APPROVER. Blocks: migration. Status: RULED 2026-08-01, run parallel

An item with an open decision gate does not enter Ready.

09
Acceptance criteria

How we agree on "finished"

Acceptance criteria are the numbered, testable statements defining when an item is finished. Agreed before the build starts, which is what makes them useful. Written afterwards, they only describe what got built.

The test for a good criterion

A person can click through the running app and mark it pass or fail without asking anyone's opinion. If two reasonable people could disagree about whether it passed, it is not a criterion yet.

Testable

  • Typing three characters into the search box filters the list to matching names within one second
  • Clearing the search box restores the full list
  • A search with no match shows "No handbooks found"

Not testable

  • Search works well
  • The UI looks better
  • Performance is improved
  • Handles errors gracefully

Given / When / Then

For anything conditional, where the result depends on the situation, use the three-part form. It forces you to state the starting conditions, which is where most ambiguity hides.

Given a BP is assigned to three clients
When they open the client Work History tab for Client A
Then only Client A's records appear

How many

Three to seven for a normal item. Fewer than three usually means the item is under-specified. More than seven usually means it is two items.

10
Estimation

Sizing the work

Story points express relative size, not hours. We use Fibonacci because the gaps widen as work gets bigger, which matches how confidence drops as work gets bigger.

An item estimated at 13 or above gets split before it is started. An item too big to size is too big to specify, and an item too big to specify is one nobody can verify.

11
Discussion

Comments and attachments

The description holds the current truth. Comments hold the history. Keeping them separate is what lets someone reconstruct a decision months later without reading a chat log.

Goes in the descriptionGoes in a comment
What we are buildingWhat happened while building it
Acceptance criteriaTest results against those criteria
Scope and out of scopeQuestions and their answers
The current plan, always up to dateA decision and the date it was made
Links to specsA handoff note saying where to test
Keep the description current

If scope changes mid-build, edit the description first, then add a comment saying what changed and why. A description describing a plan we abandoned is worse than no description, because it is confidently wrong.

Comment prefixes

Start every comment with one of six prefixes. It makes the item history scannable without reading every word.

PrefixUse forExample
DECISION:A ruling, who made it, whenDECISION: APPROVER 8/25, allow .jpg, block .docx for now.
BLOCKED:What is stopping progress and who unblocks itBLOCKED: needs the staging Stripe key. Waiting on the APPROVER.
HANDOFF:Passing work on, with where to testHANDOFF: deployed to staging, ready to verify AC 1-4.
TESTED:Verification results, criterion by criterionTESTED: AC 1, 2, 4 pass. AC 3 fails, search is case sensitive.
QUESTION:Something needed to continueQUESTION: should an inactive BP still appear in the list?
NOTE:Anything else worth keepingNOTE: reused the modal from client Work History.

Five moments that always deserve a comment

  1. Picking the item up, if anything in it is unclear.
  2. Making a decision.
  3. Getting blocked, and again when unblocked.
  4. Moving to For Testing, naming where to test and what to check.
  5. Verification passing or failing.

Attachments

Name files so they mean something: ADV-165_loading-spinner_2026-08-25.png, never Screenshot 2026-08-25 at 3.14.22 PM.png.

Attach

  • Defect screenshots, with the relevant area visible
  • Screen recordings under two minutes
  • Design mockups
  • Sanitized sample data
  • The AI prompt or spec used to build it

Do not attach

  • The only copy of a specification. Specs live in the repo
  • Long recordings. Cut to the relevant thirty seconds
  • Anything with client or employee personal information
Personal information

Never attach real client data, employee data, or any live document containing personal information, and that includes screenshots. Names, partial Social Security numbers, addresses, dates of birth, medical information, background check results and pay data all count. A screenshot of a real record is a copy of a real record. Mask the identifying fields, rebuild the screen with fake data, or describe it in words.

Link items, do not type numbers

Typing "see #165" into a title or description creates a reference no tool can follow. Use the link fields instead: mark duplicates as duplicates, set the blocker field so the board shows what is stuck, and link related work. A typed number is a note to yourself. A link is a note to the system.

Definition of Ready and Definition of Done

Two checklists. The first protects the builder from ambiguous work. The second protects the user from unverified work. Tick through them below and watch the gate flip.

Definition of Ready

All twelve before it moves to Ready

Not ready. Keep it in Backlog.

Definition of Done

All ten before it moves to Done

Not done. Keep it in For Testing.
Two things that are not Done

"It works on my machine" is not Done, because your machine is not where users are. "The AI reported it finished" is not Done, because a report is a claim, not a verification.

13
Engineering

Code and environments

Branches and commits

A branch is an isolated copy of the code where one change is built before it joins the main version. Name it after the item, so the board and the code stay connected.

type/ADV-###-short-description

feature/ADV-172-poster-select-all
fix/ADV-165-review-endless-loading
chore/ADV-175-poster-scrape-ingestion

Commit messages: first line under 72 characters, present tense, item number included. The body explains why, since the diff already shows what.

ADV-165 Fix endless loading on Send for BP Review

The review request awaited a response the endpoint never returned.
Added the response and a timeout. Verified against AC 1-3.

Self-review before In Review

Run this list on your own diff. When a second developer joins, this becomes a pull request with a required reviewer.

  • Read every line of the diff, including code you did not type yourself.
  • Does the change do only what the item asked, and nothing else?
  • Any secrets, keys, or client data in the diff?
  • Any hardcoded values that should be configuration?
  • Are error states handled rather than swallowed?
  • Are loading and empty states handled?
  • Did it touch anything on the Do not break list?
  • Are database migrations reversible?
  • Dead code, debug logging and commented-out blocks removed?

Secrets and data

  • No credentials in the repository. Environment variables only.
  • No production database access from a local machine without a reason recorded on the item.
  • No client data copied into a development environment.
  • Rotate any key ever pasted into a chat, a ticket, or an AI tool.
14
Shipping

Releases and release notes

Every release gets a written goal

One sentence: what a user can do after this ships that they could not do before. That sentence becomes the headline of the release note, so writing it at the start saves writing it at the end.

Releasing, in order

  1. Confirm every item in the release is Done, or explicitly pulled out.
  2. Write the release note.
  3. Get approval from the release approver.
  4. Deploy.
  5. Spot check the headline flow in production.
  6. Mark the release released, set the date.
  7. Post the release note internally.
Know the way back

Before deploying, know how to undo it. If a migration cannot be reversed, say so in the release note and take a database snapshot first. If a deploy goes wrong, roll back first and diagnose after.

Writing the note

Write from the user's side, not the code's side. The reader wants to know what changed for them.

Yes: "You can now search the handbook list by name."

Yes: "Sending a policy for review no longer hangs on the loading spinner."

No: "Added a filtered query to the handbook index endpoint."

No: "Fixed missing response in review request handler."

Write each line as its item reaches Done rather than reconstructing the whole note at the end. That is why "release note line written" sits on the Definition of Done.

15
AI-assisted building

When the AI writes the code

Most of our code is generated rather than typed. That changes what documentation is for, and it moves the engineering effort to the front of the process.

Three consequences

  1. A vague spec produces confidently wrong code. An AI will not stop to ask what an ambiguous line means. It will guess, and the guess will be plausible, well formatted and wrong.
  2. The spec is the only durable record. The code is an output that can be regenerated. The spec is the input that cannot.
  3. The spec is reviewable by non-developers. That is where requesters exercise control, before the build rather than after it.

Write the spec in two layers

Layer 1 · The plain-English guide

For requesters, reviewers, and your future self.

  • In one line: what this is, no jargon
  • What this is: two or three sentences anyone can follow
  • Why it matters: what it costs us today
  • What you will be able to do: the visible outcomes
  • How it fits: what comes before and after
  • Done when: the plain version of the criteria

Layer 2 · The build spec

For the AI tool and the builder.

  • Goal: the technical objective
  • Current state: files and functions involved today
  • Scope: numbered changes
  • Do not break: named flows
  • Acceptance criteria: the testable list
  • Dependencies and sequencing
  • Test notes and source references
The order matters

Layer 1 first, always. If you cannot write the plain-English version, you do not yet understand the request well enough to build it, and neither will the tool.

The AI build record

Every item built with an AI tool carries this comment, with the actual prompt or spec attached. Months from now, when something behaves oddly, the question will be "what did we ask for," and this is the only place with the answer.

NOTE: AI build record
Tool:
Date:
Spec handed to it:
Deviations: [anything the tool did differently, and why it was kept]

Reviewing code you did not write

You do not need to read every generated line to review responsibly. Check these six things.

  • Does it match the spec? Read the diff against the acceptance criteria, not against your memory of the prompt.
  • Did it wander outside scope? A one-line fix touching nine files needs an explanation.
  • What did it delete? Deletions are the highest-risk part of any generated diff.
  • Are error and empty states real, or does only the happy path look finished?
  • Any credentials, client data, or hardcoded values?
  • Does it duplicate something we already have? Generation tends to rebuild rather than reuse. Ask "do we already have this" before accepting a new helper.
The verification gate

Nothing reaches Done on an AI's report. A person opens the running app, walks each acceptance criterion, marks each pass or fail, and posts a TESTED: comment. This does not scale down for small items. Small items are exactly where unverified changes hide.

Automation

Using the Claude skills

Two Claude skills apply everything in this playbook for you. They draft to the templates, run the gates, and create the work in Zoho Sprints once you approve. Neither one writes to the board without you saying yes.

sprints-work-item

Turns a request or a defect report into a properly written Story, Task or Bug, then creates it. Classifies the type, writes the title and description, runs the Definition of Ready, searches for duplicates, and shows you everything before it touches Sprints.

Use it for: anything that is one item.

sprints-prd

Writes the ten-section PRD, then decomposes it into an epic, a release and the item list, and creates all of it. Shows you the breakdown table first and refuses to leave a release goal empty.

Use it for: anything bigger than a week, or anything carrying an open decision.

How to trigger them

Say what you want in plain language. The skill picks itself up from the phrasing.

file this as a bug create a work item add this to Sprints put this on the board turn this feedback into items write a PRD for X spec this feature break this into an epic set up a release
The pattern

Paste the raw material, say what you want, answer the questions it asks, review the draft, then approve. The skill does the formatting, the classification, the gate checks and the API calls. You do the judgment.

What happens, step by step

What it will ask you for

It asks for whatever the Definition of Ready needs and it cannot infer. Have these ready and the run takes one exchange instead of three.

It will askBecause
Steps to reproduce, for a bugA defect nobody can reproduce does not get fixed. It will not draft around a missing repro
Which epicAn item with no epic disappears from every rollup view
Priority and ownerBoth are Definition of Ready checks
An estimateOnly for items going to Ready. It will refuse to create anything sized 13 or above and will offer a split instead
A ruling on any open decisionAn item with an open decision gate cannot enter Ready
Whether a near-duplicate it found is the same workIt searches the board before creating

What they refuse to do

  • Create anything without your explicit approval.
  • Invent acceptance criteria you have not agreed to.
  • Write a description whose content is only an image.
  • Put client or employee personal information into any field, screenshots included.
  • Write a title in past tense.
  • Create an item sized 13 or above, or file an open question as an item.
  • Leave a release goal empty.

Two things they cannot do

Upload attachments

Screenshots and recordings still get attached by hand in the Sprints UI. The skill will tell you which items are waiting on one.

Verify anything

Creating an item is not building it, and building is not verifying. The human verification gate in section 12 applies exactly as before.

Glossary

Definitions

Precise meanings for every technical term in this playbook. Written for people who do not write code, and accurate enough for people who do.

Acceptance criteria process
The numbered, testable statements defining when an item is finished. Each can be checked by clicking through the running application and marked pass or fail without interpretation.Agreed before the build starts. Written afterwards, they only describe what happened.
Backlog process
The list of filed work nobody has started. Items sit here until they pass the Definition of Ready and are promoted.A backlog is a queue, not a wish list. Anything that will never be built should be closed, not left to age.
Branch code
A named, isolated line of development in the repository. Work happens on a branch so the main version of the code stays working while a change is in progress.Named after the item it implements, so the code and the board stay connected.
Bug item type
An item recording that behavior in a shipped build is wrong. The defining test is that a user can reach the broken behavior today.Distinct from a missing feature. If it never worked and was never promised, it is a Story.
Commit code
A saved, described snapshot of a set of code changes. The message explains why the change was made, since the change itself already shows what.Includes the item number so any line of code can be traced back to the request that caused it.
Decision gate (DG) gate
A numbered, unresolved business decision recorded on a PRD or an item, with a named owner and a note on what it blocks.An item with an open decision gate cannot enter Ready.
Definition of Done gate
The checklist an item passes before it is called finished. Covers verification, merge, deployment, release association, dates, and the release note line.Its purpose is to make "done" mean the same thing every time, for everyone.
Definition of Ready gate
The checklist an item passes before anyone starts building it. Covers description, criteria, epic, release, owner, priority, estimate and open decisions.Its purpose is to remove the mid-build stall where the builder has to stop and hunt for an answer.
Deploy code
Moving a version of the code to an environment where it runs. Deploying to staging makes it testable. Deploying to production makes it live for real users.A deploy is reversible if you planned the rollback first, and not otherwise.
Environment code
A running copy of the application. Local runs on the builder's machine, staging is a shared copy with fake data for verification, production is the live system real users touch.Client data belongs in production only.
Epic container
A group of items making up one capability. It answers "which capability is this part of" and lives until the capability is complete, often across several releases.Groups by what the work is, not by when it ships.
Estimate / story points process
A relative size for a piece of work on the Fibonacci scale (1, 2, 3, 5, 8, 13). Points measure size and uncertainty together, not hours.Applied only to items entering Ready. Anything sized 13 or above gets split.
Given / When / Then process
A three-part format for a conditional acceptance criterion. Given the starting conditions, When an action happens, Then this specific result follows.Useful because it forces the starting conditions to be stated, which is where ambiguity usually hides.
Item container
One piece of work on the board, typed as a Story, a Task or a Bug. Describes exactly one outcome a person could verify as working or not working.The atomic unit of the whole system. Everything else is a container for items.
Kanban process
A way of running work where items flow left to right through fixed columns, with a cap on how many can be in progress at once. There are no fixed-length sprints.Chosen over Scrum for a small team because it delivers flow control without the ceremony overhead.
Merge code
Combining the changes on a branch back into the main version of the code.Merging is the point of no return for review. Everything on the self-review checklist happens before it.
Migration code
A change to the structure of stored data, such as adding a column or moving records between tables. Risky because existing data has to move with it.Reversible migrations are a requirement, not a preference. If one cannot be reversed, snapshot first and say so in the release note.
PRD document
Product Requirements Document. The written plan for a feature agreed before it is built: the problem, the user, current and desired behavior, scope, acceptance criteria, decision gates and risks.Required for work bigger than about a week, work touching money or client data, or work carrying an open decision.
Production code
The live application real users are using right now, with real data in it.Every change reaching production has been verified by a person somewhere else first.
Pull request (PR) code
A proposal to merge one branch into the main code, opened so it can be reviewed before it lands.With a single builder, the self-review checklist stands in for the reviewer until a second developer joins.
Release container
A group of items shipping together on a planned date. It answers "which shipment is this part of" and closes on the day it deploys.An item not attached to a release cannot appear in a release note, so from the user's side it never shipped.
Release notes document
The plain-English summary of what changed for users in one release: the headline, what is new, what is fixed, known issues and the rollback note.Built from the items in the release, which is why release association is part of the Definition of Done.
Repository (repo) code
Where the code lives, along with its full change history. Also where specifications live, under /docs.Canonical for anything a future person needs to reconstruct a decision.
Rollback code
Undoing a deployment and returning to the previous working version.Plan it before deploying. When a deploy goes wrong, roll back first and diagnose after.
Staging code
A shared copy of the application, running the same code as production but with fake data, used to verify acceptance criteria before real users see the change.Never holds client data.
Story item type
An item describing a change a user would notice and could describe in their own words. Delivers value on its own.Written from the user's point of view, not the code's.
Task item type
An item describing an engineering step with no standalone user value: groundwork, configuration, migration, refactor or research.Always names the story it enables. A task enabling nothing is a task nobody needs.
WIP limit process
Work In Progress limit. The maximum number of items allowed in a column at one time. Ours is three for In Progress.Half-finished work carries all the cost of work and none of the value.
